# Implementation Task: Convert School Van Tracker from Hatchable to Render

## 1. Objective

Convert the existing School Van Tracker project into a production-oriented, standard Node.js application deployable on Render.

Repository: `https://github.com/myfavoriteworkplace/route-nest-van-tracker`

Current branch: `main`

Create a new branch named `migration/render-deployment`.

The existing project was built for Hatchable and contains:

- `public/index.html`
- `public/login.html`
- `public/app.js`
- `public/saas.js`
- `public/saas.css`
- `public/style.css`
- `api/` with individual API handler files
- `lib/tenant.js`
- `migrations/` containing six SQL migrations
- `hatchable.toml`

The current project has no `package.json` and no standard Node.js server entry point.

Do not rewrite the application from scratch. Preserve the existing UI, workflows, SQL schema, and business logic wherever possible.

The target stack is:

- Frontend: existing HTML, CSS and JavaScript
- Backend: Node.js with Express
- Database: PostgreSQL, preferably Render PostgreSQL
- Authentication: independent application authentication, not Hatchable authentication
- Billing: Razorpay subscriptions and verified webhooks
- Hosting: Render Static Site for the frontend and Render Web Service for the API
- Source control: existing GitHub repository

## 4. Create a real Node.js application

Create `package.json` with:

- A stable Node.js engine version supported by Render.
- `start` script for the production server.
- `dev` script for local development.
- `test` script.
- `db:migrate` script.
- Express and the required PostgreSQL, session, authentication, validation, security and test dependencies.

Choose compatible, maintained dependency versions and commit the generated lockfile.

Use Express as the HTTP server. The server must:

- Bind to `0.0.0.0`.
- Listen on `process.env.PORT`.
- Use `process.env.NODE_ENV` for environment-specific settings.
- Register request parsing, security middleware, session handling, API routes and centralized error handling.
- Serve static files only if a combined deployment is deliberately selected. The preferred deployment is a separate frontend Static Site and backend Web Service.
- Expose `GET /health` for Render health checks.
- Expose `GET /api/health` for API diagnostics if needed.
- Return meaningful HTTP status codes and consistent JSON errors.
- Never expose stack traces, credentials or database details in production responses.

The health endpoint should verify application readiness and, where appropriate, database connectivity. Do not report healthy if the application cannot perform its required database operations.

## 5. Replace Hatchable database access

Replace Hatchable database imports with a shared PostgreSQL connection pool using the `pg` package.

Requirements:

- Connect using `DATABASE_URL`.
- Use parameterized SQL queries.
- Configure connection timeouts and sensible pool limits.
- Handle connection failures without crashing on ordinary transient request errors.
- Close the pool gracefully on process termination.
- Keep SQL data access separate from HTTP response logic where practical.
- Do not introduce an ORM merely to perform this migration.
- Preserve existing SQL statements and business rules where possible.
- Never use an in-memory array or local JSON file as a substitute for persistent application data.

### Migration handling

Review these files in order:

- `migrations/0001_commercial_saas.sql`
- `migrations/0002_billing_provider.sql`
- `migrations/0003_school_invites.sql`
- `migrations/0004_annual_provider_plan.sql`
- `migrations/0005_single_bootstrap_admin.sql`
- `migrations/0006_profile_email.sql`

Implement a migration runner that:

1. Connects to PostgreSQL.
2. Creates a schema-migration tracking table.
3. Applies unapplied migrations in deterministic order.
4. Records successful migration versions.
5. Uses a transaction per migration where supported.
6. Stops deployment or startup with a clear error if a migration fails.
7. Never re-applies an already successful migration.
8. Never drops production tables or resets production data automatically.

Check the SQL for Hatchable-specific assumptions before running it on Render PostgreSQL.

Do not apply destructive changes to an existing database without an explicit backup and migration plan.

## 6. Replace Hatchable authentication

This is a critical migration.

The current frontend uses `window.hatchable.auth.getSession()` and `window.hatchable.auth.signOut()`. Replace these with an independent authentication system.

Prefer secure, server-managed sessions using an established session library and PostgreSQL-backed session storage. Do not use an in-memory session store in production.

Implement:

- Email-based login compatible with the existing user experience.
- A secure mechanism for issuing and verifying one-time email codes or login links.
- Expiration and single-use enforcement for codes.
- Rate limiting on login and verification endpoints.
- Generic responses that do not reveal whether an email exists.
- Secure session creation and destruction.
- Session regeneration after authentication.
- HttpOnly cookies.
- Secure cookies in production.
- Appropriate SameSite policy.
- CSRF protection for state-changing requests when cookie-based authentication is used.
- Session expiry and logout.
- Authorization checks on every protected API request.

If an email provider is needed, implement a provider adapter and configure a real provider using environment variables. Local development may use a clearly separated development-only mail transport.

Never log real login codes, passwords, session cookies or tokens in production.

### User and role model

Preserve the current roles and role-specific experiences:

- Platform Super Admin
- School Admin
- Driver
- Parent/guardian

Use the existing database model as the source of truth where possible. If the current model relies on Hatchable-managed user identities, design a migration for application-owned identities and profile mappings.

Do not assume a Hatchable user ID is interchangeable with a new identity-provider user ID.

Document the mapping and migration strategy. Do not grant administrative roles merely because someone registers with a particular email address.

### Bootstrap Super Admin

Preserve the intended one-time Super Admin bootstrap flow, but implement it independently.

- Read the bootstrap secret from `PLATFORM_BOOTSTRAP_KEY`.
- Require an authenticated, eligible account.
- Enforce one-time use atomically in the database.
- Prevent concurrent requests from creating multiple Super Admin accounts.
- Do not return the secret to the browser.
- Provide a documented secure procedure to rotate or disable the bootstrap secret after initial setup.

Do not weaken bootstrap authorization to simplify testing.

## 7. Convert every existing API handler

Convert the current Hatchable handlers to Express-compatible route handlers and services.

Preserve URL compatibility with the existing frontend where practical.

### Identity

- `GET /api/me`

Return the authenticated user's profile, platform-admin status, school memberships and role-appropriate context.

Unauthenticated requests must return `401`, not fabricated demo-user data.

### School administration

- `POST /api/schools/create`
- `GET /api/school/data`
- `POST /api/school/data`
- `GET /api/school/invite`
- `POST /api/school/invite`
- `GET /api/school/attendance`

Preserve existing behavior for school creation, vehicles, routes, students, driver/vehicle/route assignments, invitations and attendance history.

Validate every input server-side.

Every school-scoped query must enforce membership and role permissions on the server. Never trust `school_id` from the browser as proof of authorization.

### Trips and attendance

- `POST /api/trips/manage`
- `POST /api/trips/location`
- `POST /api/trips/attendance`

Preserve trip start/end operations, location updates and attendance events.

Enforce:

- The authenticated driver is assigned to the relevant school and trip.
- The trip belongs to the selected school.
- A trip cannot receive GPS updates after it has ended.
- Attendance can only be recorded by authorized users.
- Boarding, drop-off and absence events follow the existing business rules.
- Duplicate or invalid transitions are rejected or handled idempotently.
- GPS coordinates, timestamps and accuracy values are validated.
- Rate limits prevent abusive location submissions.

Use database transactions where related writes must succeed or fail together.

### Parent location

- `GET /api/parent/location`

Preserve the current parent-location behavior while enforcing verified guardian-to-student relationships.

A parent must never be able to obtain another school's or another family's location by changing a URL parameter.

Return the latest authorized location and a clear stale-location indicator.

### Platform administration

- `GET /api/platform/overview`
- `POST /api/platform/school-status`
- `POST /api/platform/billing-plan`
- `POST /api/platform/bootstrap`

Only authorized platform administrators may access or mutate platform-wide information.

Do not expose other schools' student details or operational data to ordinary school administrators.

### Billing

- `POST /api/billing/checkout`
- `POST /api/webhooks/razorpay`

Preserve the existing school-level subscription model: one subscription per school, not per student, parent or driver.

Use the existing billing-related schema and adapt it only when necessary.

## 8. Preserve tenant isolation

Treat tenant isolation as a security requirement, not a frontend feature.

Create shared authorization helpers for:

- Requiring an authenticated user.
- Requiring a platform Super Admin.
- Requiring a specific school role.
- Verifying school membership.
- Verifying driver assignment to a trip.
- Verifying a parent-to-student relationship.

The database must remain the authority for permissions.

For each request, derive the user's identity from the verified session, retrieve the relevant membership from the database and verify access to the requested resource.

Never rely solely on:

- `school_id` in a request body.
- Query parameters.
- Hidden buttons or navigation items.
- User-editable role fields.
- Data stored in browser local storage.

Add automated security tests that attempt to read and mutate School B's data while authenticated only as a School A user.

- Subscription status updates from verified provider events.
- Persistence of provider subscription and payment identifiers.

## 13. Database migration and existing data

The first deployment may use a new Render database. Do not assume the Hatchable database automatically transfers.

Document two separate procedures:

1. Fresh installation: create the database and apply all migrations.
2. Existing data migration: export permitted source data, map identity IDs, import data, validate row counts and relationships, and perform a controlled cutover.

Do not migrate passwords, session secrets or provider credentials as ordinary data.

Do not delete or modify the existing Hatchable project or database during this migration.

Before a production cutover:

- Take a recoverable backup.
- Validate schema compatibility.
- Validate student, school, membership, trip, attendance and billing relationships.
- Verify data counts and key constraints.
- Have a rollback plan.

If access to the Hatchable database is unavailable, state that a production data migration cannot yet be completed. Do not claim existing data has been migrated.

## 18. Definition of done

The migration is accepted when:

- `npm ci` succeeds from the repository root.
- `npm test` runs successfully.
- The backend starts with the documented configuration.
- The health endpoint passes.
- Every frontend API call targets the new backend.
- No required route imports the Hatchable SDK.
- No frontend code depends on `window.hatchable`.
- All critical user journeys work with persistent PostgreSQL data.
- Authentication and tenant isolation tests pass.
- Razorpay webhook signatures are verified.
- No secrets are exposed in the browser or Git history.
- The application deploys successfully to Render staging.
- All remaining limitations are documented honestly.

Begin by inspecting and documenting the existing implementation. Then implement the migration in small, reviewable stages, run tests after each stage, and report evidence rather than assuming success.
